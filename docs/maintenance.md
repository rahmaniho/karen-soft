# راهنمای نگهداری و توسعهٔ کارن سافت

این راهنما برای توسعه‌دهنده‌ای است که می‌خواهد تغییرات روزمره، دموها، محتوا و
دروازه‌های کیفیت را بدون شکستن مسیرهای موجود انجام دهد.

## پیش‌نیازها

- Node.js 22 و npm 10 (مطابق CI).
- نصب وابستگی‌ها: `npm ci`.
- متغیرهای محیطی واقعی در `.env.local`؛ هیچ کلید یا رمزی در مخزن قرار ندهید.
  فرم تماس بدون تنظیم Resend پاسخ 503 می‌دهد و نباید با دادهٔ ساختگی جایگزین شود.

## چرخهٔ عادی تغییر

```bash
npm run typecheck
npm test
npm run build
git checkout -- tsconfig.tsbuildinfo   # این فایل ردیابی می‌شود؛ بعد از build بازگردانید
npm start -- -p 3000
```

سپس در یک ترمینال دیگر:

```bash
npm run test:e2e
npm run audit:a11y
npm run audit:a11y:demos
npm run audit:routes
npm run seo:audit
```

در محیط محدود، می‌توان مسیر مرورگر را با `CHROMIUM_PATH` و کتابخانه‌های سیستمی
را با `LD_LIBRARY_PATH` مشخص کرد. برای ممیزی یک مسیر:

```bash
node scripts/a11y-routes.mjs --include-frames --settle 700 --concurrency 1 \
  --paths /portfolio/gym --out .cache/audit/a11y-one.json
```

## Design System

- پیش از افزودن کارت/دکمه/فرم جدید، از `components/ui/*` و `components/shared/resource-card.tsx` استفاده کنید. قراردادها در `docs/design-system-stage3.md` آمده است.
- کارت اطلاعاتی را `interactive` نکنید مگر واقعاً یک مقصد داشته باشد. کارت منبع باید یک لینک نام‌دار داشته باشد، نه چند لینک تودرتو.
- فرم‌ها باید `FormFeedback` را از ابتدا mount کنند و هنگام ارسال فقط محتوا/تن آن را عوض کنند؛ دادهٔ کاربر در خطای ارسال پاک نشود.
- `app/(site)/loading.tsx` سراسری اضافه نکنید. سایت عمدتاً static است؛ fallback سراسری می‌تواند H1 تکراری و وضعیت 200 برای مسیر ناشناخته بسازد. loading را فقط در segment واقعاً dynamic و همراه با تست routes/SEO اضافه کنید.
- بعد از تغییر کامپوننت مشترک، علاوه بر unit/E2E، `audit:routes` و `seo:audit` را هم اجرا کنید؛ تست مرورگر به‌تنهایی HTML اولیهٔ static را کامل پوشش نمی‌دهد.

## انتشار حساب‌یار

- منبع واحد نسخه/لینک/هش/اندازه و یادداشت تغییرات: `lib/hesabyar.ts`؛ بخش دانلود خانه و
  فهرست محصولات مشترک است و صفحهٔ اختصاصی، `llms.txt` و نقشهٔ سایت از همان داده می‌خوانند.
- پیش از تغییر لینک، مشخصات دارایی و یادداشت همان انتشار را در GitHub بررسی کنید.
  متن کنار دانلود باید همان راهنمای کوتاه مصوب مالک در `HESABYAR_UPGRADE_INSTRUCTIONS`
  بماند: پشتیبان‌گیری قبل از به‌روزرسانی؛ در صورت انجام نشدن به‌روزرسانی، حذف نسخهٔ قبلی
  و نصب فایل جدید. برچسب فنی Debug/Pre-release در متن عمومی دانلود نمایش داده نمی‌شود.
- تصویر معرفی/اشتراک‌گذاری `public/images/hesabyar/hesabyar-cover.jpg` و نشان کوچک
  `public/images/hesabyar/hesabyar-mark.png` از لوگوی رسمی ارسالی مالک ساخته شده‌اند؛
  رنگ/طرح لوگو را بدون تأیید مالک تغییر ندهید.
- بخش `#release-notes` صفحهٔ اختصاصی فقط کارت‌های تغییرات را نشان می‌دهد؛ ردیف پیوندهای
  «یادداشت انتشار رسمی در GitHub»، «دریافت فایل SHA-256» و «منبع تغییرات همین ساخت»
  به درخواست مالک از این بخش حذف شده است. بدون درخواست تازه آن را بازنگردانید.
  اطلاعات فنی در اسناد انتشار و `llms.txt` نگه‌داری می‌شوند؛ کارت مستقل نسخهٔ اندروید
  و راهنمای نصب بخش دانلود مشترک تغییر نکرده‌اند.
- چک‌لیست کامل و محدودیت اعتبارسنجی باینری: `docs/hesabyar-release-update.md`.

## دموهای نمونه‌کار

- منبع هر دمو و روش ساخت در `docs/external-demos.md` آمده است.
- بعد از هر `npm run build:demos` حتماً `npm run patch:demos` را اجرا کنید.
  وصله‌ها شامل حذف service worker دیجی‌کارن، اصلاح مسیرهای داخلی، و لایهٔ
  دسترس‌پذیری `karensoft-a11y` هستند.
- برای بازساخت فقط یک دمو: `DEMO_SRC_DIR=<clones> node scripts/build-demos.mjs --only karenwood`.
  وصله‌های upstream در `scripts/demo-patches/` نگهداری می‌شوند و اگر قبلاً اعمال
  شده باشند دوباره اعمال نمی‌شوند.
- پس از تغییر فایل‌های `public/demos/**` یا ساخت `.next`، سرور `next start` را
  yeniden راه‌اندازی کنید. هنگام build یا اجرای `next dev` نباید سرور دیگری از همان `.next` استفاده کند؛ dev و production پوشهٔ ساخت مشترک دارند و هم‌زمانی آن‌ها خروجی را خراب می‌کند.
- رنگ برند، قیمت‌ها، آمار کسب‌وکاری و ادعاهای محصول را بدون تأیید مالک تغییر ندهید.
  لایهٔ دسترس‌پذیری فقط کنتراست/نام/هدف لمسی را اصلاح می‌کند.

## محتوا و SEO

- محصولات: `lib/products.ts`؛ نمونه‌کارها: `lib/portfolio.ts`؛ نوشته‌ها: `content/blog/`.
- پس از افزودن مسیر، `sitemap` و `audit:routes`/`seo:audit` را اجرا کنید.
- ادعای رتبهٔ تضمینی گوگل، آمار ساختگی، مشتری/توصیه‌نامهٔ جعلی و فرم تزئینی ممنوع است.
- اهداف عملکرد (LCP ≤ 2.5s، INP ≤ 200ms، CLS ≤ 0.1) باید با اندازه‌گیری واقعی
  گزارش شوند، نه صرفاً در متن تسک.

## CI و استقرار

- گردش‌کار `.github/workflows/nextjs.yml` روی `main` و `arena/**` اجرا می‌شود:
  unit، build، typecheck، E2E، دسترس‌پذیری سایت و دموها، و SEO.
- برنامه از مسیرهای سروری استفاده می‌کند؛ استقرار مناسب Vercel است، نه GitHub Pages.
- خطای ساخت Cloudflare Workers در PR #49 دیده شد و در PR #50 دوباره سبز شد؛
  اگر تکرار شود، مالک باید داشبورد/لاگ آن را بررسی کند.
- قبل از تغییرات پرخطر (استقرار، DNS، پایگاه داده، سرویس تولید) پشتیبان و مسیر
  rollback مشخص کنید. این مخزن تغییر مخرب تولیدی انجام نمی‌دهد.

## خطاهای شناخته‌شده

- در ممیزی کامل ۳۸۸ بررسی سایت، گاهی خطای گذرای React #418 (hydration) زیر بار
  سنگین دیده می‌شود؛ در ۱۰۰ بارگذاری dev و ۶۰ بارگذاری production بازتولید نشد.
  CI فعلاً با `--strict-runtime` بسته نمی‌شود. Playwright در CI یک retry دارد و
  گزارشگر `github` خطای آزمون را به annotation تبدیل می‌کند؛ اگر retry هم شکست خورد،
  ابتدا اسکریپت‌های پیش از hydration (`next-themes` و `READER_BOOT_SCRIPT`) و سپس بار هم‌زمان را بررسی کنید.
- ممیزی iframe همهٔ نسخه‌های تعریف‌شده در `demoVariants` را پوشش می‌دهد؛ از جمله
  نمای ادمین دیجی‌کارن (`?admin=overview`). نسخهٔ نمایشی جدید را در `lib/portfolio.ts`
  ثبت کنید تا خودکار وارد ممیزی شود.
